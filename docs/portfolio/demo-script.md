# Demo Script · 医疗器械设备更新机会

**SIMULATED / Mock AI / Portfolio Prototype**。所有机构、角色、流程、日期均为模拟设定，不指向真实医院。产品资料留空，不添加未经核实的参数。

## 目标与准备

目标讲解节奏为约 8 分钟；这是主持脚本，不是已证实的新手录入耗时。逐条结构化审核可能超时，应提前预演。5 分钟面试可使用真实截图解释完整路径，再现场展示反证与版本；明确哪些是预先准备，不能声称全部临场生成。

启动 `node server.mjs`，打开 127.0.0.1:4173。使用隔离浏览器或新客户代号，避免覆盖已有案例。本轮截图用 `PORTFOLIO-ICU-001`，名称“模拟 A 院 · ICU”，性质 SIMULATED，项目代号 `ICU-DEMO-A`。如代号已存在，另用新代号，不覆盖。

## 时间脚本

| 时间 | 操作 | 展示与讲解 | 价值 |
|---|---|---|---|
| 00:00 | 打开工作台 | “这是医疗器械销售副驾驶原型，当前为 Mock，不是医疗或采购决策系统。” | 先说定位与边界 |
| 01:00 | 新建模拟客户，填入下方初始记录，提取并审核 | 展示原文、来源、销售判断；说明语义确认与接受不同 | Human-in-the-loop 有实际门槛 |
| 02:00 | 首次批次确认建立 V1，查看客户理解并生成假设 | 维护痛点不等于采购项目；当前 V1 阶段可能尚未评估 | 不把推测写成事实 |
| 03:00 | 生成并确认拜访计划 | “先验证影响、客户是否希望改善，再问项目是否成立。” | 以信息缺口驱动拜访 |
| 04:00 | 开始科室主任演练，问维护、响应时长、预算 | 明确模拟客户与正式 Evidence 隔离；选择行为标注、确认后发送；结束评分 | 展示 AI 工作流而非聊天 API |
| 05:00 | 填独立模拟拜访记录，提取并逐项语义审核 | 使用下方第一轮记录，不转录角色扮演 | 客户表达有独立出处 |
| 06:00 | 复盘、商机检查、接受行动并保存 V2 | Stage 4 由整组条件支持，不是一句采购启动；预算仍未知也如实显示 | 可解释的证据门槛 |
| 07:00 | 下一轮：确认计划，演练可跳过，录入独立更正 | 把采购启动更正标为 CONTRADICT；不是删除客户历史 | 反证进入结构化状态 |
| 08:00 | 复盘、Stage 3、接受动作、保存 V3、刷新并打开历史 | 当前 E1 INVALIDATED；V2 当时 Stage 4 不变 | 展示判断更新与快照保护 |

## 初始录入：V1 的资料

机构：`模拟 A 院（仅模拟设定）`；科室：`ICU`；岗位：`模拟科室主任（权限待核实）`；记录日期：`2026-09-10`；项目代号：`ICU-DEMO-A`（用于区分资料，不证明已经立项）。

客户明确表达：

```text
客户表示目前设备还能正常使用
客户表示设备维护比较麻烦
```

销售判断：`我感觉客户可能会采购，但还没有客户采购表达支持`。

待验证：

```text
是否希望改善未知
采购计划未知
预算未知
决策流程未知
```

信息提取后，机构/科室/岗位只是模拟设定。两条客户表达在编辑中分别确认 `equipment / SUPPORT`、`pain / SUPPORT`；其余不用猜测。销售判断保持 `SALES_INFERENCE`，未知保持 `UNVERIFIED`。编辑后再次接受，确认本批建立 V1。

## 演练发言

| 销售发言 | 供演示者人工确认的行为类别 |
|---|---|
| 最近维护协调主要是什么问题？ | OPEN_QUESTION |
| 维修响应需要多久？ | FOLLOW_UP |
| 预算是否已经确认？ | VERIFY_GAP |

客户不应给出无依据的预算或响应小时数。评分是人工结构化行为评价，不能说成 LLM 自动理解所有表现。演练结束后另填下面的模拟拜访记录。

## 第一轮独立模拟拜访：V2

日期 `2026-09-11`，参与人 `模拟主任、演示销售`，同项目 `ICU-DEMO-A`。在“客户明确表达”中逐行填写：

| 原文 | 人工确认 target | polarity / 补充 |
|---|---|---|
| 客户表示希望减少维护负担 | need | SUPPORT |
| 客户表示计划更新监护仪 | purchase | SUPPORT |
| 客户表示项目范围为ICU监护设备 | scope | SUPPORT，scopeValue=ICU监护设备 |
| 客户表示项目参与者包括科室与设备科 | participants | SUPPORT |
| 客户表示科室将提交更新申请 | internalAction | SUPPORT |
| 采购流程已经启动。 | procurementStarted | SUPPORT |
| 客户表示采购流程为科室提出再由设备科审核 | process | SUPPORT |
| 客户表示由院内授权委员会最终批准 | decision | SUPPORT |
| 客户表示采购时间定于2027年6月 | procurementTime | SUPPORT |

这是为了演示门槛构造的模拟记录，不是医院事实。不要补写预算金额或厂商。下一步同意仍选未知，除非有独立模拟记录明确约定。

每条编辑时保留原文/类型，选择对应命题和极性；若有多行候选，将不适用项保留 unknown/UNKNOWN。勾选语义确认、保存修改，再接受记录。之后确认批次、查看复盘与商机检查，检查为什么 Stage 4 以及还缺什么。接受本轮行动草稿、确认动作，再保存 V2。

## 第二轮独立模拟拜访：V3

点击下一轮，生成并确认计划；第二次演练可通过现有按钮跳过，不跳过记录审核。日期 `2026-09-12`，同参与人和项目，填写：

```text
之前说采购已经启动是不准确的。
```

审核 `CUSTOMER_STATED / procurementStarted / CONTRADICT` 并接受。同客户同项目同命题下，现有模型会关联原启动 Evidence。核对 `contradicts` 与旧对象的 `invalidated_by`，不能凭展示代号手工捏造 ID。

复盘与商机检查应显示 Stage 4→3；其他项目条件仍保留。确认新动作，保存 V3 并刷新，查看 V1/V2/V3。V2 的 Stage 4 与当时有效的启动 Evidence 保持不变。

## 收尾句

“我的重点不是让 AI 说客户一定会买，而是把判断的来源和更新条件做出来。这里的采购反证会改变当前阶段，但不会改写当时的历史。当前使用 Mock 与人工确认，我能够明确说明哪些是实现、哪些仍是限制。”

## 不符合预期时

停在当前步骤，查看待审核项、来源、项目、命题和阶段缺失条件。不要改规则、伪造预算、强设 Stage 或删除历史来使演示成功。使用截图说明已验证路径，并如实说明现场状态。
